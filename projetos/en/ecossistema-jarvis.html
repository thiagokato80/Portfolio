JARVIS Ecosystem

Four agents that talk over a protocol, not a shared library

An ecosystem of everyday AI agents: JARVIS orchestrates and interprets the request, Alfred holds the household memory, Lucius handles finances with its own dashboard, and Portaria gives both a shared identity. Separate processes, speaking A2A.

The problem

The easy way to build several agents is to put them all in one process, sharing objects in memory. It works in a demo and fails as architecture: the agents stop being autonomous and become functions of a monolith, and nothing you learn there transfers to a real system, where the parts run separately and can fail independently.

I wanted to test the question that matters before proposing this kind of architecture in a corporate environment: what breaks when real agents have to communicate over a protocol?

The solution

Four repositories, four processes, communicating over the A2A protocol on HTTP. None of them reaches into another's database.

  • JARVIS — the orchestrator. Interprets the request in natural language, decides who to ask, and composes the answer.
  • Alfred — the household memory. Records maintenance, suppliers and history, and answers queries with the exact data, including verbatim when that is what was asked for.
  • Lucius — the finances. Imports transactions, categorises, calculates across two date axes, forecasts, and backs its own web dashboard for lookups without going through the agent.
  • Portaria — identity and session. Born from an extraction: login left JARVIS and became a package both install, so that the same password and session serve both screens.

Two design decisions worth more than the code: the Lucius dashboard separates fact from forecast into distinct collections in the JSON, so no consumer can sum the two by accident; and every query exposes a drill-down of the rows behind each number, while declaring what was left out of the total and how much that represents.

Outcome

The full thread was executed against the real model in August 2026, with two agents live simultaneously — not with stubs. That proved what automated tests cannot: that the model name is callable and that the API honours structured response schemas.

The automated tests, by explicit decision, replace all three LLM endpoints with deterministic stubs. A test cannot depend on an API key or on an answer that varies.

The lesson that matters for a corporate setting is about integration cost: agents separated by a protocol cost more to build and return real autonomy — including the ability for one to fail without taking the others down.
